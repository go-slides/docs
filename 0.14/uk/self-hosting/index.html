Self-hosting

Обслуговуйте playground і slides --server зі своєї машини за допомогою Caddy: автоматичний HTTPS, заголовки, потрібні playground, і вхід через OpenID Connect попереду.

Ви читаєте документацію до застарілої версії; її вміст може вже бути неточним. Перейти до останньої версії.

Playground — це статичні файли, а slides --server — один процес на loopback. Обидва можна запустити на власній машині, під власним іменем, для людей, які входять через обліковий запис вашої організації. Ця сторінка робить це за допомогою Caddy (перевірено з v2.11.7), який сам отримує й поновлює сертифікати HTTPS, і oauth2-proxy для входу. Кожен показаний тут файл є в selfhost/, і його CI перевіряє кожен Caddyfile командою caddy validate.

Playground

Кожен випуск сайту додає весь сайт, разом із playground, як один tar-архів, зібраний для кореня домену, з його SHA-256:

curl -fLO https://github.com/go-slides/go-slides.github.io/releases/download/v0.1.0/go-slides-site-v0.1.0.tar.gz
curl -fLO https://github.com/go-slides/go-slides.github.io/releases/download/v0.1.0/go-slides-site-v0.1.0.tar.gz.sha256
sha256sum -c go-slides-site-v0.1.0.tar.gz.sha256
tar -xzf go-slides-site-v0.1.0.tar.gz -C /srv
mv /srv/go-slides-site-v0.1.0 /srv/go-slides-site

Архів відтворюваний: повторне збирання того самого тега дає ті самі байти. Поруч із кожним файлом, що стискається (модулі WebAssembly, шрифти, сторінки, скрипти), він містить той самий файл, стиснутий Brotli (.br) і gzip (.gz), тож сервер надсилає їх як є й нічого не стискає на льоту.

Caddyfile

slides.example.org — це ваше ім’я. Його записи A і AAAA вказують на машину, а порти 80 і 443 досягають Caddy:

import headers.caddy

slides.example.org {
	root * /srv/go-slides-site
	file_server {
		precompressed br gzip
	}
	import playground_headers
}
caddy run --config Caddyfile.playground

Після цього playground розташований за адресою https://slides.example.org/playground/.

Що має зробити правильно сервер

  • HTTPS. Caddy отримує сертифікат від Let’s Encrypt за допомогою ACME (RFC 8555), доводячи, що володіє іменем, відповіддю на порту 80 (HTTP-01) або 443 (TLS-ALPN-01), і поновлює його. Машина, до якої CA не може дістатися, може натомість використати виклик DNS-01 (запис TXT, для якого потрібен Caddy зі збіркою модуля вашого DNS-провайдера) або власний сертифікат через tls cert.pem key.pem. На тестовій машині tls internal використовує локальний CA Caddy.
  • application/wasm. Caddy надсилає цей тип для .wasm; іншому серверу може знадобитися це вказати. Playground компілює свої модулі з байтів, які прочитав (рушій експорту — у міру завантаження, у власній відповіді з цим типом), тож він запускається навіть із сервера, що надсилає інший тип; з nosniff правильний тип усе ж той, який слід надсилати.
  • Стиснення. precompressed br gzip надсилає playground.wasm.br браузеру, що приймає Brotli, .gz — тому, що приймає gzip, і сам файл в іншому разі, з Vary: Accept-Encoding. Модуль редактора має близько 7 МіБ у Brotli проти 33 МіБ без стиснення.
  • Кешування. Сторінка запитує кожен модуль, воркер, шрифт і картинку з випуском у запиті (playground.wasm?v=v0.1.0), тож їх можна зберігати рік (immutable). Самі сторінки перевіряються повторно (no-cache): новий випуск видно при наступному візиті.
  • Заголовки в headers.caddy:
(playground_headers) {
	header {
		Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval'; worker-src 'self'; connect-src 'self' https:; img-src 'self' data: blob: https:; media-src 'self' data: blob: https:; style-src 'self' 'unsafe-inline' https:; font-src 'self' data: blob: https:; frame-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'self'"
		X-Content-Type-Options nosniff
		Referrer-Policy no-referrer
		Strict-Transport-Security "max-age=31536000"
	}
	@versioned query v=*
	header @versioned Cache-Control "public, max-age=31536000, immutable"
	@unversioned not query v=*
	header @unversioned Cache-Control "no-cache"
}

Політика — та, що потрібна playground: його скрипти (завантажувач вбудований), його WebAssembly ('wasm-unsafe-eval') і його воркер, усе з вашого сервера. Зображення, таблиці стилів і шрифти презентації можуть надходити з будь-якої адреси https:, як і у виводі команди; приберіть https: з img-src, style-src, font-src, media-src і connect-src, щоб тримати кожен запит на вашому сервері, і презентації, що вказують деінде, показуватимуться без цих ресурсів. Сама презентація працює в iframe, ізольованих без вашого походження, під суворішою власною політикою, яку playground записує в кожен фрейм: вона не може дістатися ні до playground, ні до його сховища, ні до ваших cookie, що б не казав цей заголовок. frame-ancestors 'self' не дає іншим сайтам вбудовувати playground у фрейми.

  • Ні COOP, ні COEP. Playground не використовує ні SharedArrayBuffer, ні потоків, тож йому не потрібна міжджерельна ізоляція. Надсилання Cross-Origin-Embedder-Policy: require-corp заблокувало б зображення презентації з інших сайтів.

Без мережі

Щойно сторінку завантажено, усе відбувається в браузері: редактор, попередній перегляд, вигляд доповідача й експорти PDF, PPTX та ODP, шрифти яких є в архіві. Презентація не надсилається ні на ваш сервер, ні кудись іще. Мережі потребує те, що називає презентація: зображення чи таблиці стилів за адресою https: і веб-шрифт теми gaia, який вона запитує в fonts.bunny.net (без нього слайди переходять на інший шрифт). Посилання на цю документацію ведуть за межі вашого сервера.

slides --server за проксі

slides --server залишається на 127.0.0.1, а Caddy перенаправляє до нього. Сервер перевіряє заголовок Host кожного запиту й Origin WebSocket живого перезавантаження, проти DNS rebinding і сторінок інших сайтів, а проксі зберігає публічне ім’я в обох. --allowed-host додає це ім’я до того, що приймають перевірки; вони лишаються ввімкненими:

slides -s --allowed-host decks.example.org /srv/decks
decks.example.org {
	reverse_proxy 127.0.0.1:8080
}

Живе перезавантаження проходить як є (Caddy проксіює WebSocket без налаштування). Не використовуйте для цього --host 0.0.0.0: він віддає теку всій мережі, в обхід проксі та його входу.

--allowed-host є у v0.14.0 і пізніших: go install github.com/go-slides/slides/cmd/slides@v0.14.0.

Вхід через OpenID Connect

Caddy питає oauth2-proxy про кожен запит (forward_auth). oauth2-proxy відповідає 202 для браузера, що увійшов, і тоді Caddy його обслуговує, та 401 в іншому разі, і тоді Caddy перетворює це на перенаправлення на вхід. Вхід — це потік коду авторизації OpenID Connect Core 1.0: браузер іде до вашого провайдера (Keycloak, Authentik, Entra ID, Google, Okta, Dex…), повертається на /oauth2/callback з кодом, oauth2-proxy обмінює код на ID Token, перевіряє його й ставить власний cookie.

  1. Зареєструйте клієнта у вашого провайдера, конфіденційного, з потоком коду авторизації. Його redirect URI, які мають збігатися точно: https://slides.example.org/oauth2/callback та https://decks.example.org/oauth2/callback.
  2. Покладіть секрети у файли, читані лише oauth2-proxy: секрет клієнта, без символу нового рядка наприкінці, і секрет cookie рівно з 32 випадкових байтів (head -c 32 /dev/urandom). Їх записує ваше сховище секретів (облікові дані systemd, секрети Docker чи Kubernetes, Vault…); жоден не потрапляє до файлу конфігурації, командного рядка чи змінної середовища, де їх показують логи та ps.
  3. Налаштуйте oauth2-proxy (oauth2-proxy.cfg):
http_address = "127.0.0.1:4180"
reverse_proxy = true
trusted_proxy_ips = ["127.0.0.1/32", "::1/128"]
upstreams = ["static://202"]
set_xauthrequest = true

provider = "oidc"
oidc_issuer_url = "https://id.example.org/realms/example"
client_id = "go-slides"
client_secret_file = "/run/secrets/oauth2-proxy-client-secret"
code_challenge_method = "S256"

redirect_url = "/oauth2/callback"
whitelist_domains = ["slides.example.org", "decks.example.org"]
email_domains = ["example.org"]

cookie_secret_file = "/run/secrets/oauth2-proxy-cookie-secret"
cookie_secure = true
cookie_samesite = "lax"

redirect_url без хоста повертає вхід кожного сайту на його власний callback, тож кожен сайт має власний cookie. whitelist_domains — це те, куди вхід може повернутися: якщо його просять піти кудись інде, він залишається на вашому сайті. trusted_proxy_ips вірить заголовкам X-Forwarded-* лише від Caddy. email_domains каже, хто може увійти; oauth2-proxy має також параметри для груп і списків адрес.

  1. Налаштуйте Caddy (Caddyfile.oidc):
import headers.caddy

(signed_in) {
	handle /oauth2/* {
		reverse_proxy 127.0.0.1:4180
	}
	handle {
		forward_auth 127.0.0.1:4180 {
			uri /oauth2/auth
			copy_headers X-Auth-Request-User X-Auth-Request-Email
			@unauthorized status 401
			handle_response @unauthorized {
				redir * /oauth2/sign_in?rd={scheme}://{hostport}{uri} 302
			}
		}
		{block}
	}
}

slides.example.org {
	import signed_in {
		root * /srv/go-slides-site
		file_server {
			precompressed br gzip
		}
		import playground_headers
	}
}

decks.example.org {
	import signed_in {
		reverse_proxy 127.0.0.1:8080
	}
}
slides -s --allowed-host decks.example.org /srv/decks
oauth2-proxy --config /etc/oauth2-proxy/oauth2-proxy.cfg
caddy run --config Caddyfile.oidc

oauth2-proxy і slides слухають лише на loopback: єдиний вхід — через Caddy, а отже, через авторизацію. Заголовки playground розміщено всередині блока signed-in, лише для playground: сторінка входу oauth2-proxy є формою, яку зупинив би їхній form-action 'none'.

Альтернатива — caddy-security, модуль Caddy, що робить вхід усередині Caddy, без другого процесу. Йому потрібен Caddy, зібраний із модулем (xcaddy), і власна мова конфігурації.

Перевірка 

curl -sI -H 'Accept-Encoding: br' 'https://slides.example.org/playground/playground.wasm?v=v0.1.0'

Відповідь містить content-type: application/wasm, content-encoding: br і cache-control: public, max-age=31536000, immutable, а також наведений вище content-security-policy. Якщо попереду стоїть вхід, той самий запит без cookie відповідає 302 на /oauth2/sign_in.

Джерела

  • Caddy: automatic HTTPS, file_server, header, reverse_proxy, forward_auth.
  • RFC 8555, ACME: HTTP-01 (8.3), DNS-01 (8.4).
  • OpenID Connect Core 1.0: потік коду авторизації (3.1), redirect URI (3.1.2.1), ID Token (2).
  • oauth2-proxy: configuration, OpenID Connect provider.
