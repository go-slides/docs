Autoalojamiento

Sirva el playground y slides --server desde su propio equipo con Caddy: HTTPS automático, las cabeceras que necesita el playground y un inicio de sesión OpenID Connect por delante.

Está leyendo la documentación de una versión obsoleta; es posible que su contenido ya no sea exacto. Ir a la última versión.

El playground son archivos estáticos, y slides --server es un solo proceso en el bucle local. Ambos pueden ejecutarse en su propio equipo, con su propio nombre, para personas que inician sesión con la cuenta de su organización. Esta página lo hace con Caddy (probado con v2.11.7), que obtiene y renueva por sí mismo los certificados HTTPS, y oauth2-proxy para el inicio de sesión. Todos los archivos que se muestran aquí están en selfhost/, y su CI comprueba cada Caddyfile con caddy validate.

El playground

Cada versión del sitio adjunta el sitio completo, playground incluido, como un solo tarball construido para la raíz de un dominio, con su SHA-256:

curl -fLO https://github.com/go-slides/go-slides.github.io/releases/download/v0.1.0/go-slides-site-v0.1.0.tar.gz
curl -fLO https://github.com/go-slides/go-slides.github.io/releases/download/v0.1.0/go-slides-site-v0.1.0.tar.gz.sha256
sha256sum -c go-slides-site-v0.1.0.tar.gz.sha256
tar -xzf go-slides-site-v0.1.0.tar.gz -C /srv
mv /srv/go-slides-site-v0.1.0 /srv/go-slides-site

El tarball es reproducible: construir de nuevo la misma etiqueta da los mismos bytes. Junto a cada archivo que se comprime (los módulos WebAssembly, las fuentes, las páginas, los scripts), lleva el mismo archivo comprimido con Brotli (.br) y gzip (.gz), de modo que el servidor los envía tal cual y no comprime nada al vuelo.

Caddyfile

slides.example.org es su nombre. Sus registros A y AAAA apuntan al equipo, y los puertos 80 y 443 llegan a Caddy:

import headers.caddy

slides.example.org {
	root * /srv/go-slides-site
	file_server {
		precompressed br gzip
	}
	import playground_headers
}
caddy run --config Caddyfile.playground

El playground queda entonces en https://slides.example.org/playground/.

Lo que el servidor debe hacer bien

  • HTTPS. Caddy obtiene el certificado de Let’s Encrypt con ACME (RFC 8555), demostrando que posee el nombre al responder en el puerto 80 (HTTP-01) o 443 (TLS-ALPN-01), y lo renueva. Un equipo al que la CA no puede llegar puede usar en su lugar el desafío DNS-01 (un registro TXT, que requiere un Caddy compilado con el módulo de su proveedor de DNS), o su propio certificado con tls cert.pem key.pem. En un equipo de pruebas, tls internal usa la CA local de Caddy.
  • application/wasm. Caddy envía este tipo para .wasm; en otro servidor puede que haya que indicarlo. El playground compila sus módulos a partir de los bytes que ha leído (el motor de exportación mientras se descarga, en una respuesta propia con ese tipo), así que arranca incluso desde un servidor que envía otro tipo; con nosniff, el tipo correcto sigue siendo el que hay que enviar.
  • Compresión. precompressed br gzip envía playground.wasm.br a un navegador que acepta Brotli, .gz a uno que acepta gzip, y el archivo mismo en caso contrario, con Vary: Accept-Encoding. El módulo del editor pesa unos 7 MiB en Brotli, frente a 33 MiB sin comprimir.
  • Caché. La página pide cada módulo, worker, fuente e imagen con la versión en la consulta (playground.wasm?v=v0.1.0), de modo que se pueden conservar durante un año (immutable). Las páginas en sí se revalidan (no-cache): una versión nueva se ve en la siguiente visita.
  • Las cabeceras de headers.caddy:
(playground_headers) {
	header {
		Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval'; worker-src 'self'; connect-src 'self' https:; img-src 'self' data: blob: https:; media-src 'self' data: blob: https:; style-src 'self' 'unsafe-inline' https:; font-src 'self' data: blob: https:; frame-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'self'"
		X-Content-Type-Options nosniff
		Referrer-Policy no-referrer
		Strict-Transport-Security "max-age=31536000"
	}
	@versioned query v=*
	header @versioned Cache-Control "public, max-age=31536000, immutable"
	@unversioned not query v=*
	header @unversioned Cache-Control "no-cache"
}

La política es la que necesita el playground: sus scripts (el cargador está en línea), su WebAssembly ('wasm-unsafe-eval') y su worker, todos desde su servidor. Las imágenes, hojas de estilo y fuentes de una presentación pueden venir de cualquier dirección https:, como en la salida del comando; quite https: de img-src, style-src, font-src, media-src y connect-src para mantener todas las peticiones en su servidor, y las presentaciones que apunten a otra parte se mostrarán sin esos recursos. La presentación en sí se ejecuta en iframes aislados (sandbox) sin su origen, bajo una política propia más estricta que el playground escribe en cada marco: no puede llegar al playground, a su almacenamiento ni a sus cookies, diga lo que diga esta cabecera. frame-ancestors 'self' impide que otros sitios incrusten el playground en un marco.

  • Ni COOP ni COEP. El playground no usa SharedArrayBuffer ni hilos, así que no necesita estar aislado entre orígenes. Enviar Cross-Origin-Embedder-Policy: require-corp bloquearía las imágenes de una presentación procedentes de otros sitios.

Sin red

Una vez cargada la página, todo ocurre en el navegador: el editor, la vista previa, la vista del presentador y las exportaciones a PDF, PPTX y ODP, cuyas fuentes están en el tarball. La presentación no se envía ni a su servidor ni a ningún otro sitio. Lo que necesita la red es lo que la presentación nombra: imágenes u hojas de estilo en una dirección https:, y la fuente web del tema gaia, que pide a fonts.bunny.net (sin ella, las diapositivas recurren a otra fuente). Los enlaces a esta documentación salen de su servidor.

slides --server detrás del proxy

slides --server se queda en 127.0.0.1 y Caddy le reenvía las peticiones. El servidor comprueba la cabecera Host de cada petición y el Origin del WebSocket de cada recarga en vivo, contra el DNS rebinding y las páginas de otros sitios, y el proxy conserva el nombre público en ambos. --allowed-host añade ese nombre a lo que aceptan las comprobaciones; estas siguen activas:

slides -s --allowed-host decks.example.org /srv/decks
decks.example.org {
	reverse_proxy 127.0.0.1:8080
}

La recarga en vivo pasa tal cual (Caddy hace de proxy de los WebSockets sin configuración). No use --host 0.0.0.0 para esto: serviría el directorio a toda la red, saltándose el proxy y su inicio de sesión.

--allowed-host está en v0.14.0 y posteriores: go install github.com/go-slides/slides/cmd/slides@v0.14.0.

Inicio de sesión con OpenID Connect

Caddy consulta a oauth2-proxy en cada petición (forward_auth). oauth2-proxy responde 202 a un navegador que ha iniciado sesión, y Caddy entonces lo sirve, y 401 en caso contrario, que Caddy convierte en una redirección al inicio de sesión. El inicio de sesión es el flujo de código de autorización de OpenID Connect Core 1.0: el navegador va a su proveedor (Keycloak, Authentik, Entra ID, Google, Okta, Dex…), vuelve a /oauth2/callback con un código, oauth2-proxy intercambia el código por un ID Token, lo comprueba y establece su propia cookie.

  1. Registre un cliente en su proveedor, confidencial, con el flujo de código de autorización. Sus URI de redirección, que deben coincidir exactamente: https://slides.example.org/oauth2/callback y https://decks.example.org/oauth2/callback.
  2. Ponga los secretos en archivos que solo oauth2-proxy pueda leer: el secreto del cliente, sin salto de línea al final, y un secreto de cookie de exactamente 32 bytes aleatorios (head -c 32 /dev/urandom). Su almacén de secretos los escribe (credenciales de systemd, secretos de Docker o Kubernetes, Vault…); ninguno va en un archivo de configuración, una línea de comandos ni una variable de entorno, donde los registros y ps los muestran.
  3. Configure oauth2-proxy (oauth2-proxy.cfg):
http_address = "127.0.0.1:4180"
reverse_proxy = true
trusted_proxy_ips = ["127.0.0.1/32", "::1/128"]
upstreams = ["static://202"]
set_xauthrequest = true

provider = "oidc"
oidc_issuer_url = "https://id.example.org/realms/example"
client_id = "go-slides"
client_secret_file = "/run/secrets/oauth2-proxy-client-secret"
code_challenge_method = "S256"

redirect_url = "/oauth2/callback"
whitelist_domains = ["slides.example.org", "decks.example.org"]
email_domains = ["example.org"]

cookie_secret_file = "/run/secrets/oauth2-proxy-cookie-secret"
cookie_secure = true
cookie_samesite = "lax"

redirect_url sin host devuelve el inicio de sesión de cada sitio a su propio callback, de modo que cada sitio conserva su propia cookie. whitelist_domains es adonde puede volver un inicio de sesión: si se le pide ir a cualquier otro sitio, se queda en el suyo. trusted_proxy_ips solo cree las cabeceras X-Forwarded-* que vienen de Caddy. email_domains indica quién puede entrar; oauth2-proxy también tiene opciones para grupos y listas de direcciones.

  1. Configure Caddy (Caddyfile.oidc):
import headers.caddy

(signed_in) {
	handle /oauth2/* {
		reverse_proxy 127.0.0.1:4180
	}
	handle {
		forward_auth 127.0.0.1:4180 {
			uri /oauth2/auth
			copy_headers X-Auth-Request-User X-Auth-Request-Email
			@unauthorized status 401
			handle_response @unauthorized {
				redir * /oauth2/sign_in?rd={scheme}://{hostport}{uri} 302
			}
		}
		{block}
	}
}

slides.example.org {
	import signed_in {
		root * /srv/go-slides-site
		file_server {
			precompressed br gzip
		}
		import playground_headers
	}
}

decks.example.org {
	import signed_in {
		reverse_proxy 127.0.0.1:8080
	}
}
slides -s --allowed-host decks.example.org /srv/decks
oauth2-proxy --config /etc/oauth2-proxy/oauth2-proxy.cfg
caddy run --config Caddyfile.oidc

oauth2-proxy y slides escuchan solo en el bucle local: la única entrada pasa por Caddy y, por tanto, por el inicio de sesión. Las cabeceras del playground van dentro del bloque con sesión iniciada, solo en el playground: la página de inicio de sesión de oauth2-proxy es un formulario, que su form-action 'none' bloquearía.

La alternativa es caddy-security, un módulo de Caddy que hace el inicio de sesión dentro de Caddy, sin un segundo proceso. Necesita un Caddy compilado con el módulo (xcaddy) y su propio lenguaje de configuración.

Compruébelo 

curl -sI -H 'Accept-Encoding: br' 'https://slides.example.org/playground/playground.wasm?v=v0.1.0'

La respuesta indica content-type: application/wasm, content-encoding: br y cache-control: public, max-age=31536000, immutable, con el content-security-policy de arriba. Con el inicio de sesión por delante, la misma petición sin cookie responde 302 a /oauth2/sign_in.
