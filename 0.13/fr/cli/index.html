Ligne de commande

Toutes les commandes et options de slides, et le fichier de configuration slides.yaml.

Vous lisez la documentation d’une version obsolète : son contenu peut ne plus être exact. Aller à la dernière version.
Cette page décrit la v0.13.0.
slides [deck.md] [flags]
slides [command] [flags] deck.md

Commandes

CommandeRôle
buildécrit la présentation en HTML, en PDF ou en images (voir plus bas). Commande par défaut : slides deck.md équivaut à slides build deck.md
expandaffiche la présentation en Markdown Marp ordinaire : gabarits développés, types de diapositives (kinds) remplacés par les directives qu’ils représentent
notesaffiche les notes de l’orateur
kindsliste les kinds que la présentation peut utiliser et ce qu’ils définissent ; --json (depuis la v0.6.0) les écrit sous la forme [{"name", "extends", "directives": [{"key", "value"}]}], extends étant résolu
themesliste les thèmes
versionaffiche la version (tout comme slides --version)
completionaffiche un script de complétion pour le shell : bash, zsh, fish ou powershell

slides <command> --help affiche les options d’une commande. Les options peuvent précéder ou suivre la présentation : slides deck.md -o out.html et slides -o out.html deck.md reviennent au même. Les options longues prennent deux tirets (--html) ; -o est la seule option courte. build écrit deck.html à côté de deck.md, sauf si -o en décide autrement.

Plusieurs présentations, et un répertoire

Depuis la v0.6.0, build accepte plusieurs présentations, un répertoire (les présentations qu’il contient, trouvées récursivement) ou un motif, et en génère jusqu’à --parallel simultanément. - désigne l’entrée standard ; contrairement à marp-cli, un tube n’est lu que si - le demande.

Un motif est interprété comme le fait le glob de marp-cli (** et {a,b} depuis la v0.7.0 ; mettez-le entre guillemets pour que le shell le laisse à slides) : *, ?, [a-z] et {md,txt} dans un nom, ** pour un nombre quelconque de répertoires, si bien que 'docs/**/*.md' prend les présentations de toute l’arborescence. Un joker n’atteint pas un nom qui commence par un point, rien n’est cherché dans node_modules, la casse compte (*.md ne trouve pas UPPER.MD), et tout ce qu’un motif sélectionne est converti, quelle que soit son extension. Un motif qui ne sélectionne rien est une erreur.

  • -I dir trouve les fichiers Markdown (.md, .mdown, .markdown, .markdn, en minuscules) sous dir, comme marp-cli : node_modules et les répertoires commençant par un point sont ignorés. Avec -o out, chaque présentation est écrite à son chemin sous dir, reproduit sous out : dir/sub/b.md donne out/sub/b.html (b.pdf, b.001.png, b.txt, … selon les options). Sans -o, les sorties sont écrites à côté de leurs présentations. Nommer des présentations en plus de -I est une erreur, de même que -o file pour plusieurs présentations (-o - est autorisé).
  • -P n génère n présentations simultanément. Le rendu d’une présentation exploite déjà les cœurs, donc n est plafonné à leur nombre ; avec -o -, les présentations sont générées l’une après l’autre. Les messages d’une présentation restent groupés, et une présentation en échec n’arrête pas les autres : le code de sortie vaut 1 et le message liste les échecs.

Transitions et page de présentation

Depuis la v0.6.0, la directive transition de marp-cli fonctionne : <!-- transition: fade 1s -->, un nom et une durée facultative, pour la diapositive et les suivantes, ou <!-- _transition: cover --> pour une seule. Les noms intégrés sont ceux de marp-cli : clockwise, counterclockwise, cover, coverflow, cube, cylinder, diamond, drop, explode, fade, fade-out, fall, flip, glow, implode, in-out, iris-in, iris-out, melt, overlap, pivot, pull, push, reveal, rotate, slide, star, swap, swipe, swoosh, wipe, wiper et zoom ; none la désactive. La page la joue avec la View Transition API du navigateur quand le spectateur quitte vers l’avant la diapositive qui la porte, et quand il y revient ; les navigateurs sans cette API changent de diapositive comme avant, et un spectateur qui demande des mouvements réduits obtient un simple fondu. Un thème peut apporter ses propres images clés, nommées marp-transition-NAME (ou marp-outgoing- et marp-incoming-, et -backward), qui passent avant celles qui sont intégrées.

La page comporte le contrôleur à l’écran — précédent, page, suivant, plein écran —, qui apparaît quand le pointeur bouge ou qu’une touche est pressée et disparaît au bout d’un moment (--bespoke.osc=false le supprime), ainsi que, avec --bespoke.progress, une barre de progression. La barre de progression est désormais désactivée par défaut, comme dans marp-cli ; elle était auparavant toujours affichée.

Mode présentateur

Depuis la v0.7.0, la page dispose du mode présentateur de marp-cli. Appuyez sur p, ou sur le dernier bouton du contrôleur : une fenêtre s’ouvre avec la diapositive courante, l’étape suivante, vos notes de l’orateur, la page, l’heure et un chronomètre (cliquez sur le chronomètre pour le remettre à zéro ; + et - redimensionnent les notes ; la barre entre les diapositives et les notes peut être déplacée). Les deux fenêtres se suivent dans les deux sens : les touches fléchées, un clic sur l’étape suivante ou sur Précédent/Suivant dans l’une font avancer l’autre, un fragment à la fois.

Il fonctionne comme celui de marp-cli, d’après ses sources 4.5.1 : la fenêtre est ?view=presenter&sync=KEY du même fichier, l’étape suivante est la même page en ?view=next dans un cadre, et les fenêtres partagent leur position par localStorage (bespoke-marp-sync-KEY) : il ne demande ni serveur ni réseau, et ne fonctionne pas dans un navigateur dépourvu de localStorage (le bouton le signale). Les notes sont du texte : &, < et > sont échappés, si bien qu’une note ne peut jamais être du balisage. Elles figurent dans la page, masquées, pour que le mode présentateur les reprenne, ce qui les tient à l’écart de ce qu’un lecteur d’écran lit au public. Les pages --bare n’ont rien de tout cela. Ce mode ajoute environ 10 Ko à une page.

Vue d’ensemble

Depuis la v0.8.0, appuyez sur o (ou Escape : marp-cli bascule avec les deux), sur le bouton en grille du contrôleur ou sur le compteur de pages du mode présentateur : toutes les diapositives s’affichent en entier dans une grille par-dessus la page. Les touches fléchées choisissent une diapositive (haut et bas par rangée), Home et End vont aux extrémités, et les autres fenêtres suivent ; Enter, Space ou un clic choisit une diapositive et, par-dessus la page, ferme la vue d’ensemble. Par-dessus le mode présentateur, un choix la laisse ouverte (le présentateur choisit la diapositive à montrer et continue à regarder). Le bouton « Close overview », o et Escape la ferment. C’est celle de marp-cli : la page, de nouveau dans un cadre, à ?view=overview&sync=KEY, qui partage la position par localStorage, sans réseau. Les diapositives de la grille peuvent recevoir le focus et portent le libellé « Slide N », et la vue d’ensemble fermée est inerte : les personnes qui naviguent au clavier ou au lecteur d’écran n’y tombent jamais. Les deux vues ajoutent ensemble environ 15 Ko à une page.

Fichiers de configuration

marp-cli lit ses options dans un fichier du répertoire de travail, et slides aussi, quand le fichier contient des données : .marprc (YAML, le JSON étant aussi du YAML), .marprc.json, .marprc.yaml, .marprc.yml, .config/marprc*, ou la clé marp de package.json ; --config-file (-c) désigne n’importe quel fichier JSON ou YAML, marp.config.json par exemple. Seul le répertoire de travail est examiné, pas ses parents, comme dans la recherche de marp-cli. Un fichier JavaScript ou TypeScript (marp.config.js …) est un programme, que slides n’exécute pas : il le signale et continue. Les options sont celles de la documentation de marp-cli qui ont un sens ici : title, description, author, keywords, url, ogImage, lang, theme, themeSet, html, allowLocalFiles, template, bespoke, inputDir, output, parallel, pdf, pptx, notes, pdfNotes, pdfOutlines, images, image, imageScale, jpegQuality, watch, server, preview ; les chemins sont relatifs au fichier. La ligne de commande l’emporte. engine, options et browser* nécessitent le moteur de Marp et un navigateur ; ils sont ignorés avec un avertissement, tout comme les options --browser* : les scripts écrits pour marp-cli continuent de fonctionner. (slides.yaml et slides.hcl, avec les kinds et les données de gabarit, sont distincts et lus comme avant.)

Surveillance, serveur et aperçu

Depuis la v0.6.0, avec les routes et le protocole de rechargement à chaud de marp-cli (lus dans ses sources 4.5.1 et comparés à un marp -s en cours d’exécution).

slides --server dir (-s) sert le répertoire sur http://127.0.0.1:8080/ (la variable d’environnement PORT change le port ; un port déjà utilisé est une erreur, signalée comme telle) :

RequêteRéponse
/deck.mdla présentation en HTML, convertie à la demande
/deck.md?pdf, ?pptx, ?png, ?jpg (ou ?jpeg), ?notes (ou ?txt)la présentation convertie selon la requête ; le PPTX est servi en pièce jointe
un répertoireson index.md ou son PITCHME.md en tant que page, sinon un index avec un lien PDF et un lien PPTX pour chaque présentation
tout autre fichierle fichier
une présentation dont la conversion échoue503, avec l’erreur

Une page ouvre un WebSocket vers /.__marp-cli-watch-notifier__/<id>, où l’id est le SHA-256 du chemin de la présentation ; le serveur envoie ready, puis reload quand la présentation, ou quoi que ce soit sous le répertoire, change. Un répertoire demandé sans sa barre oblique finale est redirigé vers celle-ci (marp-cli y sert son index, ce qui casse les liens relatifs de la page).

--watch (-w) génère les présentations, puis régénère celle qui change et, quand un fichier --theme-set, un fichier de kinds ou de données, ou la configuration change, toutes. Les pages qu’il écrit ouvrent une socket sur l’interface de bouclage (port 37717, ou le suivant qui est libre) et se rechargent quand leur présentation est régénérée. Une présentation dont la génération échoue est signalée et reste surveillée. --preview (-p) ouvre le navigateur par défaut sur le serveur, ou sur les pages HTML tout juste générées ; il n’a pas de fenêtre propre, puisque slides n’a aucun navigateur à piloter.

Le serveur est une porte d’entrée sur la machine : il est donc plus strict que celui de marp-cli, qui écoute sur toutes les interfaces et ne vérifie rien :

  • il écoute sur 127.0.0.1 ; --host change cela, avec un avertissement, et une adresse générique ne permet plus de vérifier l’en-tête Host ;
  • l’en-tête Host doit être un nom de bouclage (localhost, 127.0.0.1, [::1], *.localhost) ou l’hôte sur lequel il écoute, ce qui bloque le DNS rebinding ;
  • l’Origin d’un WebSocket doit être celle du serveur ; les sockets du mode surveillance acceptent aussi l’origine null d’une page ouverte depuis un fichier ; une requête venant d’un autre site qui n’est pas une navigation (un script, une image, un fetch) est refusée ;
  • un chemin est normalisé, ses liens symboliques sont résolus, et le résultat doit se trouver dans le répertoire : .. et un lien qui en sort sont refusés, de même que ?pdf sur une présentation extérieure ; les noms commençant par un point (.git, .env) ne sont pas servis ;
  • seulement GET et HEAD ; quelques conversions à la fois ; au plus 4096 répertoires surveillés, et aucun dans node_modules ni sous un répertoire commençant par un point.

Derrière un reverse proxy, --allowed-host name (après la v0.13.0, répétable) ajoute le nom public du proxy aux Host et Origin acceptés ; les contrôles restent actifs et le serveur reste sur la boucle locale. Auto-hébergement le place derrière Caddy, avec HTTPS et une authentification.

Métadonnées de la page

La ligne de commande l’emporte sur la présentation, comme dans marp-cli, où les options sont ajoutées à la présentation sous la forme d’un dernier commentaire de directive. Règles lues dans marp-cli 4.5.1 et vérifiées par des tests sur sa sortie (depuis la v0.6.0) :

  • Une présentation qui ne définit pas de title prend le texte de son premier titre du niveau le plus élevé, tel qu’il est écrit (# **Bold** title donne **Bold** title). Sans titre, il n’y a pas de <title>.
  • Les keywords sont découpés aux virgules, débarrassés des espaces et dédoublonnés ; une liste dans le front matter est reprise telle quelle. Comme marp-cli, la page porte la balise keywords à partir du deuxième mot-clé, et non pour un seul.
  • Une url invalide (non absolue) est ignorée avec un avertissement, et la valeur précédente conservée ; une URL valide écrit aussi <link rel="canonical"> et og:url.
  • author et description sont accompagnés de leurs équivalents Open Graph ; og:image:alt et la grande carte Twitter nécessitent à la fois un titre et une image.

Images, PDF, PPTX et ODP

-o avec une extension .pdf, .pptx, .odp, .png ou .jpg choisit le format, comme marp-cli. Les répertoires de sortie sont créés. Un PDF comporte une page par diapositive, à la taille de la diapositive, et un plan des diapositives et de leurs titres.

Notes et plan du PDF

Depuis la v0.6.0, le PDF prend en charge les deux options de marp-cli, comparées avec les PDF qu’écrit marp-cli 4.5.1 pour la même présentation :

  • --pdf-notes place les notes de l’orateur de chaque diapositive sur sa page sous forme d’annotation de type note : une icône Note jaune en bas à gauche, dont le contenu est constitué des notes (plusieurs commentaires séparés par une ligne vide) et dont le titre est l’author de la présentation. --pdf-notes seul demande un PDF, comme dans marp-cli.
  • Le plan contient un signet en gras « Page N » pour chaque diapositive et, en dessous, les titres de la diapositive imbriqués par niveau (--pdf-outlines.pages et --pdf-outlines.headings choisissent ces deux parties). Le plan est activé par défaut ici et désactivé dans marp-cli. slides en a toujours écrit un ; il coûte quelques centaines d’octets et rend une longue présentation navigable : ce choix par défaut est donc conservé. --pdf-outlines=false, ou le --no-pdf-outlines de marp-cli, le désactive, et =false sur .pages ou .headings supprime la partie correspondante. Un signet de titre renvoie à sa diapositive ; marp-cli fait en plus défiler jusqu’au titre.

Le rendu est assuré par go-webengine et le PDF est écrit par go-pdfkit ; les polices demandées par les thèmes intégrés (Lato, Roboto Mono) proviennent de go-opentype/fonts et sont intégrées : aucun rendu n’accède au réseau. Il n’y a pas de Chrome.

--image-scale 2 fait le rendu à deux pixels physiques par pixel CSS. Les images locales sont refusées sauf si --allow-local-files est indiqué, et même alors seuls les fichiers situés sous le répertoire de la présentation sont lus : une présentation venue d’ailleurs ne peut pas atteindre ~/.ssh. Les arrière-plans multiples et partagés (![bg left:40%]) sont rendus comme les calques de Marp.

--pptx écrit la présentation avec la fonction WritePresentation de go-ooxml, avec les notes de l’orateur et les métadonnées de la présentation. Depuis la v0.5.0, les diapositives sont modifiables (voir ci-dessous) ; --pptx-raster écrit une image pleine diapositive par diapositive, comme marp-cli, à une échelle de 2 par défaut que --image-scale remplace. LibreOffice ouvre le résultat. Seul LibreOffice a été testé ; PowerPoint et Keynote ne l’ont pas été.

--odp écrit une présentation OpenDocument, au moyen de la fonction WritePresentation de go-odf, avec ses notes de l’orateur ; --odp-raster écrit une image par diapositive.

PPTX et ODP modifiables

Depuis la v0.5.0, les diapositives d’un PPTX ou d’un ODP sont modifiables — le PPTX de marp-cli est une image par diapositive, et son option expérimentale --pptx-editable convertit un PDF au moyen de LibreOffice. Ici, chaque diapositive est dessinée à partir de sa mise en page, celle-là même que dessinent les exports PNG et PDF :

  • chaque ligne de texte est une zone de texte placée à sa position dans la mise en page, dans les polices avec lesquelles la diapositive a été mise en page — intégrées au fichier, si bien qu’elle a le même aspect sur une machine dépourvue de Lato ou d’Inter (vérifié avec LibreOffice 25.8) — avec le gras, l’italique, les couleurs, l’espacement des lettres et les liens cliquables ;
  • les arrière-plans, les bordures et les cadres arrondis sont des formes ; les dégradés sont des remplissages en dégradé dans le PPTX et des images dans l’ODP (un dégradé ODF n’a que deux couleurs) ;
  • les images ne sont stockées qu’une fois, quel que soit le nombre de diapositives qui les affichent ;
  • ce qu’une diapositive ne peut pas exprimer — un élément sous opacity, un filter, une ombre floue, une formule — devient une image de cet élément, son texte étant conservé par-dessus.

Rendue à nouveau par LibreOffice, une diapositive ne s’écarte que de 0,04 à 2 % des pixels de l’export PNG. --pptx-raster et --odp-raster conservent une image par diapositive.

PDF vectoriel

Depuis la v0.4.0, le PDF est dessiné en vectoriel : go-webengine peint la diapositive mise en page dans le PDF au lieu de la peindre en pixels. Le texte reste du texte, dans les polices avec lesquelles la diapositive a été mise en page, intégrées sous forme de sous-ensembles avec une table /ToUnicode : on peut le sélectionner, y rechercher et le copier. Les arrière-plans, les bordures et les dégradés sont des tracés et des ombrages, une image affichée sur plusieurs diapositives n’est intégrée qu’une fois, et les liens sont cliquables. La présentation de référence de 100 diapositives pèse 758 Kio, contre 837 Kio pour marp-cli et 10 Mio pour le PDF en images de la v0.3.0, et elle est écrite en 0,3 s.

Un élément sans forme vectorielle ici — sous opacity < 1, avec un filter ou une rotation, une box-shadow floue, un dégradé dont l’opacité s’estompe — est dessiné comme un bitmap de ce seul élément, son texte étant posé dessus de façon invisible pour rester sélectionnable. Les formules sont encore des bitmaps. --pdf-raster écrit une image par page, comme le faisait la v0.3.0.

PDF accessible et balisé

Depuis la v0.12.0, le PDF vectoriel est balisé. Il porte sa structure logique, qu’un lecteur d’écran lit dans l’ordre, comme il lit une page web :

Dans la présentationDans le PDF
une diapositiveune section (Sect)
# … ######H1 … H6
un paragraphe, une liste, un tableauP ; L avec l’étiquette et le corps de chaque élément ; Table, cellules d’en-tête avec leur portée
un lienun Link, sa zone cliquable comprise, son texte comme description
une imageune Figure avec son texte alternatif ; ![](…) sans texte alternatif est décoratif
$…$, $$…$$une Formula, sa source TeX comme description
du codeCode, sans ses numéros de ligne ni ses pastilles d’annotation
<span lang="fr">un segment dans cette langue
arrière-plans, bordures, numéros de pagedes artefacts, qu’un lecteur ignore
notes de l’orateur (--pdf-notes)des annotations dans la structure

Le fichier déclare PDF/UA-1, la norme du PDF accessible. Il porte le title de la présentation, que la visionneuse affiche, et sa lang (--lang si la présentation n’en définit pas, en sinon).

Une présentation vérifiée avec veraPDF satisfait PDF/UA-1, sauf si ses propres titres enfreignent l’ordre qu’impose la norme. PDF/UA demande que le premier titre soit un H1 et qu’aucun niveau ne soit sauté (# puis ###). Seul l’auteur de la présentation peut corriger cela. Le PDF de Chrome pour la même présentation, celui qu’écrit marp-cli, est lui aussi balisé, mais enfreint sept des règles de PDF/UA, n’a pas de section par diapositive et pas de formules.

Baliser la présentation de référence de 100 diapositives coûte 4% en taille (788 contre 757 Kio) et aucun temps mesurable. --pdf-tags=false écrit le PDF sans balises.

slides.yaml

Un fichier de configuration placé à côté de la présentation s’y applique : un dossier de présentations peut ainsi en partager un seul :

kinds: kinds.yaml        # a mapping of kinds, or file(s) holding one
themes:                  # theme CSS files or directories
  - themes/
data:                    # template data
  company: Example Inc.
html: false              # allow all raw HTML
lang: en

Kinds : les kinds: propres à la présentation remplacent ceux du fichier et de la ligne de commande. Données : les data du fichier et de la ligne de commande remplacent celles du front matter de la présentation, si bien qu’une même présentation peut être générée avec des données différentes.
